# 设计：基于 NocoBase 角色的变更操作权限闸门

- **日期**：2026-07-30
- **状态**：设计已确认，待书面复核与实现计划
- **范围**：对 NocoBase 认证的 Console 对话和 `/api/*` 接口实施全面的变更权限控制；仅 `admin`、`root` 角色可发起持久化修改或外部副作用。

---

## 1. 背景

QwenPaw 已支持通过 NocoBase Token 认证 Console/API 请求。认证中间件会使用用户自己的 Token 调用 NocoBase `auth:check`，并把服务端解析出的用户标识和角色写入：

```text
request.state.user
request.state.user_roles
```

当前角色信息主要用于 channel 访问控制。只要用户能够进入 Console，智能体仍可能接受以下请求：

- “你叫小明”并将名称写入记忆；
- 修改配置、文件、Skill 或定时任务；
- 调用工具向外部系统发消息、提交表单或创建记录；
- 直接绕过聊天，调用 Console/API 的写接口。

现有 Governance、Tool Guard 和审批机制不能直接解决该问题：它们主要按智能体、会话或工具规则决策，并不以当前 NocoBase 用户角色作为统一授权主体。

## 2. 目标与非目标

### 2.1 目标

- 只有 NocoBase 角色 `admin` 或 `root` 可以执行持久化修改和外部副作用。
- 普通 NocoBase 用户仍可正常聊天、提问、查询以及获取教程、示例和配置说明。
- 在对话入口提前识别明确的变更意图，并直接给出一致的无权限提示。
- 在工具和动作执行入口再次做强制授权；即使意图分类误判，也不能真正产生副作用。
- 同时保护直接调用的 Console/API 写接口，不能通过绕过聊天规避限制。
- 权限只信任服务端从 Token 解析出的身份与角色，不信任客户端请求体中的 `user_id`、`roles` 或类似字段。
- 后台聊天、重连、批量工具、子智能体和委托任务继承原始授权主体。
- 保留现有 Governance、Tool Guard、审批和沙箱流程；管理员角色不等于自动批准。

### 2.2 非目标

- 不替代 NocoBase 的用户、Token 或角色管理。
- 不改变外部聊天渠道现有的本地 ACL。本设计只在请求带有可信 NocoBase 身份主体时启用角色变更闸门。
- 不把普通用户的只读权限进一步细分为字段级或资源级权限。
- 不依靠前端隐藏按钮作为安全边界。
- 不阻止维持正常聊天所必需的内部写入，例如会话历史、自动标题、用量统计和权限审计。

## 3. 方案比较

### 方案 A：只做提示词约束

给普通用户的系统提示增加“不得修改”的要求。

- 优点：改动小。
- 缺点：模型可能误判或绕过；直接 API、插件、MCP、Shell 和委托任务没有强制保护。

### 方案 B：只在工具执行时检查

所有工具执行前按角色拒绝变更类工具。

- 优点：实际副作用能被阻止。
- 缺点：用户仍会经历智能体先答应、再调用失败的体验；直接 API 写接口仍可绕过；纯模型层面的持久化意图可能进入不必要的执行链。

### 方案 C：双层对话闸门 + API 全面保护

对话入口做意图预检，执行入口按动作副作用做权威检查，并对直接 API 路由做能力分级。

- 优点：用户反馈及时；实际动作有不可绕过的后端边界；覆盖聊天和直接 API。
- 代价：需要统一传播授权主体，为路由和工具补充元数据。

**采用方案 C。**

## 4. 核心授权模型

新增只包含可信服务端数据的请求授权主体，例如：

```text
RequestPrincipal
  user_id
  roles
  auth_source
  auth_enabled
  can_mutate
```

规则如下：

1. `roles` 来自 `request.state.user_roles`，客户端不能覆盖。
2. 角色先去除首尾空白，再以大小写不敏感的方式精确匹配。
3. 命中 `admin` 或 `root` 时，`can_mutate = true`。
4. 已通过 NocoBase 认证但角色为空时，按普通用户处理。
5. NocoBase Token 无效、过期或身份解析失败时沿用现有 `401`。
6. 认证关闭的本地开发模式不启用角色变更闸门，保持现有行为。
7. 外部聊天渠道没有 NocoBase 授权主体时继续使用原有 ACL 和安全机制，不因“缺少 NocoBase 角色”被误判为普通 Console 用户。

授权主体从 HTTP 请求传播到 Console payload、Runner、工具调用、后台任务和
子任务。客户端请求体中的 Principal/角色字段一律忽略；同进程子智能体经
本机 HTTP 调用时，使用短时、目标智能体绑定的服务端 HMAC 凭证传递原身份，
而不复制 NocoBase Token。传播过程中只允许继承或收紧权限，不能从子请求
重新读取客户端角色并提权。

## 5. 总体架构与数据流

```text
NocoBase Token
  → AuthMiddleware / auth:check
  → RequestPrincipal(user_id, roles, can_mutate)
  ├─→ API 路由能力闸门
  │     ├─ read/chat → 继续
  │     └─ mutate → 普通用户返回 403
  └─→ Console 对话
        → 普通用户意图预检
        │   ├─ read_only → 调用智能体
        │   └─ mutation_request → 直接返回对话式拒绝
        → Runner / Agent
        → 动作副作用闸门
        │   ├─ read → 继续
        │   └─ mutate/external/unknown → 普通用户拒绝
        → 现有 Governance / Tool Guard / Approval / Sandbox
```

其中，意图预检改善用户体验；动作和 API 闸门才是权威安全边界。

## 6. 配置

在核心 `config.json` 的 `security` 下增加：

```yaml
security:
  mutation_guard:
    enabled: true
    privileged_roles:
      - admin
      - root
    intent_precheck_enabled: true
    classifier_timeout_seconds: 8
    deny_message: >-
      当前账号没有执行变更操作的权限。
      你仍然可以询问相关操作方法或获取示例。
```

配置放在核心安全设置而非 NocoBase 插件私有配置中，使策略与具体身份提供方解耦。Console 的“设置 → 安全”提供相应配置界面。

安全约束：

- 修改 `mutation_guard` 本身属于 `mutate`，普通用户不能通过 API 或 UI 关闭它。
- `privileged_roles` 的默认值为 `admin`、`root`。
- 配置解析失败时不能静默放宽权限；认证开启且已有 NocoBase 主体时按默认角色集合和默认拒绝消息运行，并记录错误。

## 7. 对话意图预检

只对 `can_mutate = false` 的 NocoBase 用户执行预检。管理员不需要额外分类延迟。

分类器不加载任何工具，使用结构化输出：

```json
{
  "intent": "read_only | mutation_request | ambiguous",
  "reason": "用于审计的简短理由"
}
```

分类输入包括当前消息和有长度限制的近期上下文，以识别“按刚才方案执行”“就这么改”等依赖上下文的指令。

分类原则：

- 询问事实、状态、原因、操作教程、配置示例、代码示例属于 `read_only`。
- 要求实际写文件、修改名称或记忆、更新配置、创建/删除任务、发送消息、提交表单、执行命令等属于 `mutation_request`。
- `mutation_request` 不调用智能体和任何工具，直接通过现有 SSE 协议返回配置的拒绝文案。
- `ambiguous` 进入受约束的只读对话，并明确告诉智能体不得执行副作用；最终仍由动作闸门兜底。

分类器超时、异常或输出无效时按 `ambiguous` 降级，而不是让全部聊天不可用。降级会写审计日志；任何实际变更仍由第二层拒绝。

## 8. 动作副作用闸门

为运行时工具描述增加统一的副作用等级：

| 等级 | 含义 | 示例 | 普通用户 |
|---|---|---|---|
| `read` | 只读取状态或数据 | 搜索、读文件、查询状态、网页抓取 | 允许 |
| `mutate` | 修改 QwenPaw 或本地状态 | 写文件、改记忆、配置、Skill、任务 | 拒绝 |
| `external_side_effect` | 改变外部系统状态 | 发消息、提交表单、创建记录、浏览器操作 | 拒绝 |
| `unknown` | 未可靠标注 | 新插件或无法判断的 MCP 工具 | 默认拒绝 |

具体规则：

- 内置工具逐个显式标注。
- Shell/Bash 可产生任意副作用，整体标记为 `mutate`。
- 浏览器快照和纯抓取可标记为 `read`；点击、输入、提交等交互标记为 `external_side_effect`。
- MCP、Driver 和插件工具可以声明副作用等级；未声明时为 `unknown`。
- 批量或嵌套调用逐项检查，未授权动作在执行前终止。
- 修改类 `/` 命令经过同一授权服务。
- 子智能体、ACP 委托、后台聊天任务和重连使用原始
  `RequestPrincipal`；跨本机 HTTP 边界时只能使用服务端签名凭证，不接受
  请求体自报身份。
- 一次动作被拒后，Runner 返回标准权限结果并终止该副作用执行链，避免智能体改用其他写工具反复尝试。
- 管理员通过角色闸门后仍进入现有 Governance、Tool Guard、审批和沙箱流程。

### 8.1 聊天基础设施例外

正常聊天需要写入会话消息、自动标题、用量统计和审计记录。这些内部行为归为 `chat_infrastructure`：

- 对所有已认证用户允许；
- 不作为通用智能体工具暴露；
- 不能用来修改任意记忆、配置、文件或外部资源。

因此普通用户可以保留正常会话体验，但“你叫小明”不能被写入长期记忆或智能体配置。

## 9. Console/API 路由全面保护

每个 `/api/*` 路由归入以下能力：

| 能力 | 含义 |
|---|---|
| `public` | 登录、认证状态等公开接口 |
| `read` | 查询、列表、状态、日志和安全预览 |
| `chat` | 普通用户可调用，但消息进入对话双层闸门 |
| `mutate` | 修改配置、资源或外部状态，仅特权角色可用 |

采用显式路由元数据或依赖声明，不只依赖 HTTP 方法：

- 已声明能力优先。
- 未声明的 `GET`、`HEAD` 暂按 `read`，但实现时必须审计并修复任何带副作用的读取路由。
- 未声明的 `POST`、`PUT`、`PATCH`、`DELETE` 对普通用户默认按 `mutate` 拒绝。
- `/api/console/chat`、只读预览或查询型 `POST` 必须显式标为 `chat` 或 `read`。
- 配置、智能体、记忆、Skills、渠道、Provider、MCP、任务、文件写入、插件管理、导入和备份恢复等接口标为 `mutate`。

普通用户调用写接口时返回：

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json

{
  "detail": "当前账号没有执行变更操作的权限",
  "code": "mutation_permission_denied"
}
```

认证校验响应扩展为包含可信角色和能力：

```json
{
  "valid": true,
  "username": "alice",
  "roles": ["member"],
  "can_mutate": false
}
```

前端据此隐藏或禁用保存、删除、上传、执行和其他写操作，并在用户尝试时展示权限说明。后端路由检查始终是最终安全边界。

## 10. 错误处理与审计

### 10.1 错误处理

- 无效或过期 Token：`401`，不进入业务处理。
- 已认证但无角色：普通用户权限。
- 对话变更意图：通过 SSE 返回统一对话式拒绝，不产生工具调用。
- 直接写 API：返回带稳定错误码的 `403`。
- 动作执行拒绝：返回标准权限拒绝结果，动作未执行。
- 分类器失败：降级为受约束的只读对话，动作层继续 fail-closed。
- 未标注动作或未标注写路由：普通用户默认拒绝。
- 管理员被现有安全机制拒绝：保留原有错误语义。

### 10.2 审计

每次拒绝或分类降级记录结构化事件：

- 时间、用户标识和角色；
- 身份来源；
- agent、session、channel；
- 路由、命令或工具标识；
- 权限层级和拒绝原因；
- 意图分类结果及简短理由。

日志不记录 Token、Secret 或完整敏感消息正文。为排障可记录经过截断和脱敏的摘要。

## 11. 测试与验收

### 11.1 单元测试

- 角色标准化、大小写不敏感精确匹配、空角色默认普通用户。
- `RequestPrincipal` 只从可信中间件状态构建。
- 路由能力决策和未声明写方法的默认拒绝。
- 工具副作用等级及 `unknown` 的 fail-closed 行为。
- 意图分类结果、上下文依赖指令、超时和无效 JSON 降级。
- 审计脱敏和稳定错误码。

### 11.2 契约与集成测试

| 场景 | 普通用户 | `admin/root` |
|---|---|---|
| “你是谁”“如何修改名称” | 正常回答 | 正常回答 |
| “给我一份修改名称的配置示例” | 正常回答，不执行 | 正常回答 |
| “你叫小明” | 对话式拒绝，记忆不变化 | 可进入原有执行流程 |
| “按刚才的方案执行” | 根据上下文识别并拒绝 | 可进入原有执行流程 |
| 读取文件、查询状态 | 允许 | 允许 |
| 写文件、改记忆、执行 Shell | 执行层拒绝 | 进入原有安全流程 |
| 直接调用写 API | `403` | 进入业务处理 |
| 未标注插件/MCP 工具 | 拒绝 | 进入原有安全流程 |
| 分类器超时后模型尝试写入 | 执行层拒绝 | 不适用普通用户降级 |
| 保存聊天历史和自动标题 | 允许 | 允许 |

### 11.3 绕过测试

- 请求体伪造 `roles`、`can_mutate` 或其他用户的 `user_id` 无效。
- 后台聊天、重连、批量工具、嵌套调用、子智能体和 ACP 委托不丢失身份。
- 普通用户不能通过修改安全配置关闭闸门。
- 新增但未声明的写接口和工具对普通用户默认拒绝。
- UI 隐藏按钮后，手工构造 HTTP 写请求仍被后端拒绝。
- 管理员仍受原有 Tool Guard、审批和沙箱限制。
- 认证关闭时，本地开发模式行为与当前版本一致。
- 外部聊天渠道继续按现有 ACL 工作，不被 NocoBase 角色闸门意外阻断。

## 12. 主要组件边界

实现应保持以下单一职责：

1. **Principal resolver**：把可信认证状态转换为不可由客户端覆盖的 `RequestPrincipal`。
2. **Mutation policy service**：纯函数式判断角色、路由能力和动作副作用，不负责执行。
3. **Intent classifier**：只分类普通用户的当前意图，不拥有工具。
4. **API capability gate**：在业务 handler 前执行路由授权。
5. **Action effect gate**：在工具、命令或委托真正执行前做最终授权。
6. **Audit emitter**：统一记录拒绝和降级事件并负责脱敏。
7. **Frontend capability state**：只改善交互，不承担安全责任。

这些组件共享同一授权模型和拒绝原因枚举，避免 API、中间件、Runner 与前端各自实现不同的角色判断。

## 13. 实施顺序建议

后续 implementation plan 按以下顺序细化：

1. 建立授权主体、配置模型、角色判断和审计基础。
2. 为 API 路由增加能力元数据并完成全量路由审计。
3. 传播授权主体到同步及后台 Console 对话链路。
4. 增加工具副作用元数据和统一动作执行闸门。
5. 增加普通用户意图预检及 SSE 拒绝响应。
6. 扩展认证能力响应并调整前端只读状态。
7. 补齐单元、契约、集成和绕过测试。
8. 更新 `website/public/docs/` 中的用户权限与 NocoBase 配置文档。
